# 대화록 방법론 — 느낀 바 → 개선점 → 솔루션

## 목적

행정을 “경험”으로만 두지 않고, **재사용 가능한 개선 재료**로 바꾸기 위함이다.

## 한 편의 구조 (필수 섹션)

```markdown
# 대화록 · YYYY-MM-DD · [짧은 제목]

- 트랙: DW | BL | DC | CROSS (복합)
- 참여자: (예: 보호자, AI, 요약 전용)
- 장소/창구: (예: 동 행정복지센터 · 전화 · 온라인)
- 민감정보: 없음 / 가명 처리함

## 1. 상황 (Fact)
무엇이 일어났는가. 날짜·창구·요청 내용·받은 답.

## 2. 느낀 바 (Feel)
당사자·보호자가 몸으로 느낀 것. 수치 없이도 된다. 감정 단어 허용.

## 3. 개선점 (Gap)
제도·안내·연계·시간·태도·정보 비대칭 중 **어디가 비었는지**.
- 가능하면 “누가 / 무엇을 / 언제” 단위로.

## 4. 솔루션 스케치 (Fix)
당장이라도 시도할 수 있는 것부터.
- 개인 대응 (체크리스트, 질문 리스트)
- 창구 제안 (안내문 한 장, 연계 번호)
- 제도·서비스 아이디어 (중장기)

## 5. 다음 한 걸음 (Next)
48시간 안에 할 일 1~3개. 담당(가정 내 역할) 명시.

## 6. 원문·링크 (Optional)
관련 고시·안내 URL, 내부 메모 경로. 개인정보 제외.
```

## 파일 위치

| 종류 | 경로 |
|------|------|
| 템플릿 | `docs/dialogue/_TEMPLATE.md` |
| 대화록 본문 | `docs/dialogue/YYYY-MM-DD-slug.md` |
| 트랙 메모 | `docs/tracks/*.md` |
| 솔루션만 모음 | `docs/solutions/*.md` |
| 날것 캡처(비정제) | `logs/YYYY/MM/` — 나중에 대화록으로 정제 |

## 품질 기준 (짧게)

1. **Fact와 Feel을 섞지 않는다.** 느낀 바 섹션에 추측 법령 해석을 넣지 말 것.  
2. **Blame보다 Gap.** 사람 탓보다 프로세스 빈칸.  
3. **Fix는 검증 가능해야 한다.** “정부가 알아서”만 쓰지 말 것.  
4. **CROSS 트랙**이면 세 축 중 어디가 겹쳤는지 한 줄로 표시.

## 랜딩과의 관계

- 랜딩은 **헌장 + 트랙 + 최근 대화록 요약 + 솔루션 카드**를 보여 준다.  
- 본문은 GitHub `docs/`에 두고, 랜딩은 링크로 연결한다.  
- 댓글(Giscus)은 “경험 공유·정정”용이며, 법적 상담이 아니다.
