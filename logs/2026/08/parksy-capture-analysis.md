# ParksyCapture — 대화 캡처 앱의 지식관리적 의미

> helena_phone 생태계에서 ParksyCapture가 차지하는 위치와, 이것이 단순한 "캡처 도구"를 넘어 왜 지식 관리의 핵심 인프라인지 분석.

## 1. 상황 — ParksyCapture가 뭐고 왜 깔았나

### 앱 스펙

`com.parksy.capture` — 183MB. Android Share Intent로 LLM 대화 로그를 캡처해 마크다운 파일로 저장하는 앱.

**작동 방식:**
```
Claude 앱에서 대화 중 → 공유 버튼 → ParksyCapture 선택
→ Share Intent로 EXTRA_TEXT(대화 내용) 수신
→ 마크다운(.md) 파일로 로컬 저장
→ helana_log 레포에 커밋·푸시 연동
```

**실제 캡처 예:** `helana_log/logs/2026/07/ParksyLog_20260725_080708.md` — Boss와 AI 간의 실제 대화가 그대로 .md 파일로 저장된 첫 사례.

### 왜 깔았나 — 4가지 동기

| 동기 | 내용 |
|------|------|
| **① 클립보드 한계** | Claude 앱에서 긴 대화는 "전체 선택"이 끊김. 중간에 코드블록·이미지 있으면 선택이 분절됨 |
| **② 사고 흐름 보존** | AI와의 대화는 "질문→답변→반박→수정→결정"의 흐름. 결과만 남기면 판단 과정이 소실됨 |
| **③ 실행기록+판단기록 통합** | 실행 로그("뭘 했는지")만 있고 판단 로그("왜 그렇게 했는지")가 없으면 반쪽. 합쳐야 완전한 교재 |
| **④ 검색 가능한 2차 두뇌** | GitHub에 저장하면 모든 대화가 grep/searchable. "그때 그 결정 왜 했더라?"를 텍스트 검색으로 찾음 |

## 2. 느낀 바 — 그냥 캡처 도구가 아니었다

### 발견 #1: 대화가 자산이 된다

ParksyCapture를 설치하기 전까지, AI와의 대화는 "하고 나면 사라지는 것"이었다. 캡처하기 시작하면서 Boss는 이걸 깨달았다:

> **"AI와 나눈 대화 자체가 원고다. 이걸 구조화만 하면 그대로 웹페이지가 된다."**

이 통찰이 ParksyCapture → Tistory HTML 파이프라인의 시발점이다.

### 발견 #2: 이미지는 사라진다

ParksyCapture의 구조적 한계: Android Share Intent는 `EXTRA_TEXT`(텍스트)만 보낸다. Claude CDN에 호스팅된 이미지는 인증이 필요해서 외부 앱이 가져올 수 없다. 이미지가 중간에 끼어 있으면 그 이미지 자리만 비어 있고 텍스트는 이어진다.

이 한계가 오히려 **투트랙 캡처 전략**을 낳았다:

| 스레드 유형 | 캡처 방식 |
|------------|----------|
| 텍스트 전용 | ParksyCapture 단독 (완전 자동) |
| 이미지 섞인 스레드 | 텍스트 = ParksyCapture + 이미지 = 갤러리 스크린샷 → 타임스탬프 병합 |

### 발견 #3: 로그는 정제되기 전에 '날것'으로 존재해야 한다

helana_log의 설계 철학: `logs/`는 날것(raw) 캡처 공간이고, `docs/dialogue/`는 정제된 대화록이다.

```
logs/YYYY/MM/ParksyLog_*.md   →  날것 (비정제 원본)
    ↓ 사람+AI가 검토·정제
docs/dialogue/YYYY-MM-DD.md   →  정제본 (Fact/Feel/Gap/Fix/Next 구조)
```

이 2단계 구조가 중요한 이유: **날것은 가공하기 전에 사라진다.** 정제할 시간이 없으면 날것이라도 남겨야 한다. 나중에 정제할 수 있다. 날것조차 없으면 영원히 사라진다.

## 3. 빈틈 — ParksyCapture가 메꾸는 지식 관리의 구멍

### 기존 지식 관리의 3대 실패 모드

| 실패 모드 | 증상 | ParksyCapture의 해결 |
|-----------|------|---------------------|
| **판단 소실** | "왜 그렇게 했는지"가 사라지고 "뭘 했는지"만 남음 | 대화 전체를 캡처 → 질문·반박·결정의 맥락이 보존됨 |
| **기억 왜곡** | 며칠 지나면 "내가 그때 왜 그 선택을 했지?" 기억이 흐려짐 | 타임스탬프 + 원본 텍스트로 정확한 복기 가능 |
| **전수 불가** | 나 혼자 아는 암묵지. 남에게 설명하려면 처음부터 다시 생각해야 함 | 대화록 자체가 교재. "어떻게 생각이 진화했는지"가 그대로 보임 |

### 지식의 3층 구조

ParksyCapture가 있음으로써 가능해진 지식의 층위:

```
Layer 1 — 날것 (Raw)
  ParksyCapture 로그, 스크린샷, 음성 메모
  ↙ "있기만 해도 가치 있는" 층

Layer 2 — 정제 (Refined)  
  Fact/Feel/Gap/Fix/Next 구조화된 대화록
  ↙ "읽으면 이해되는" 층

Layer 3 — 발행 (Published)
  Tistory HTML 인터랙티브 페이지, YouTube 튜토리얼, Naver 퀼트
  ↙ "찾아서 배울 수 있는" 층
```

이 3층 구조가 없으면: Layer 3만 있으면 과정이 안 보이고, Layer 1만 있으면 검색이 안 된다. **셋이 다 있어야 지식이 산다.**

## 4. 솔루션 — 상호 연동 구조

### 전체 파이프라인에서 ParksyCapture의 위치

```
┌─────────────────────────────────────────────────────────┐
│                    지식 생산 파이프라인                      │
├─────────┬──────────┬──────────┬──────────┬─────────────┤
│ 캡처     │ 저장      │ 정제      │ 변환      │ 발행         │
│ (Capture)│ (Store)   │ (Refine) │ (Convert) │ (Publish)   │
├─────────┼──────────┼──────────┼──────────┼─────────────┤
│ParksyCap│helana_log│Claude·   │parksy_to │Tistory·     │
│Share    │logs/     │Boss 검토 │_html.py  │GitHub·      │
│Intent   │          │          │          │YouTube·Naver│
└─────────┴──────────┴──────────┴──────────┴─────────────┘
```

### 구체적 연동 경로

| 단계 | 도구 | 입력 → 출력 |
|------|------|------------|
| ① 캡처 | ParksyCapture | Claude 대화 → `.md` 파일 |
| ② 저장 | git push | `.md` → `helana_log/logs/` |
| ③ 트리거 | GitHub Actions | push 감지 → workflow 실행 |
| ④ 변환 | parksy_to_html.py | `.md` → CSS-only 인터랙티브 HTML |
| ⑤ 전송 | @helana_logbot | HTML 코드 → Telegram 메시지 |
| ⑥ 발행 | Boss 복사+붙여넣기 | Telegram → Tistory HTML 모드 |
| ⑦ 회수 | tistory_sync.sh | Tistory RSS → `helana_log/기자/` |
| ⑧ 출판 | GitHub Pages | `기자/` → 칠판보드 웹페이지 |
| ⑨ 전시 | YouTube·Naver | 칠판보드 → 튜토리얼·퀼트 |

### 핵심: 양방향 순환

```
ParksyCapture ──→ helana_log ──→ Tistory ──→ RSS ──→ helana_log ──→ GitHub Pages
     ↑                                                                    │
     └────────────────── YouTube · Naver · 검색 ←──────────────────────────┘
```

**데이터가 한 방향으로만 흐르는 게 아니라, 발행된 콘텐츠가 다시 로그 저장소로 돌아온다.** 이게 단순한 "백업"과 다른 점. 기록 → 발행 → 재기록의 선순환.

## 5. 다음 — 이게 왜 중요한가

### AI 시대 지식 관리의 역설

AI와 대화할수록 **더 많은 지식이 생산**되지만, 동시에 **더 빨리 사라진다.** 채팅 인터페이스는 휘발성이다. 스레드가 길어지면 컨텍스트 윈도우 밖으로 밀려나고, 새 세션을 시작하면 모든 게 리셋된다.

**ParksyCapture의 진짜 가치:** AI와의 대화를 휘발성 채팅에서 → 영구 지식 자산으로 전환하는 **인터페이스 계층**이다.

### 전통적 지식 관리 vs ParksyCapture 기반 지식 관리

| | 전통적 KM | ParksyCapture KM |
|---|----------|-----------------|
| **입력** | 사람이 수동으로 문서화 | 대화가 자동으로 기록됨 |
| **구조** | 폴더·태그·카테고리 (부담) | 날것 보존 → 나중에 정제 (무부담) |
| **판단** | 결과만 기록 | 질문·반박·수정·결정 전 과정 |
| **검색** | 제목·키워드 의존 | 전문(full-text) 검색 |
| **재사용** | 복사+붙여넣기 | 자동 변환 파이프라인 |
| **소유** | 플랫폼 종속 | GitHub git — 영구·이식 가능 |

### 한 줄 정의

**ParksyCapture는 "생각의 스크린샷" 도구다.**

코드 스크린샷이 아니라, **AI와의 사고 흐름**을 찍는 도구. 그 스크린샷(마크다운 로그)을 구조화된 지식으로 승격시키는 파이프라인이 그 위에 올라간다.

### 최종 의의

> **ParksyCapture 없이 AI와 일하는 것은, 저장 버튼 없는 워드프로세서로 글 쓰는 것과 같다.**
> 
> 결과물은 있지만, 어떻게 그 결과물에 도달했는지는 영원히 사라진다.
> 그리고 AI 시대에, "어떻게 도달했는가"는 "무엇을 만들었는가"만큼 중요하다.
> 왜냐하면 다음 질문을 더 잘하기 위한 재료이기 때문이다.
